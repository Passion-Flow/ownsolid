# 0077: Read published training files without writer ownership

- Status: proposed; private owner candidate dc2db707, standalone gateway acceptance open
- Date: 2026-11-13
- Scope: TRN-101 and DAT-101 owner interfaces, ARC-111 integration handoff

## Context

The separate Agent gateway constructs its dataset/training graph without file
stores. A real dispatched training claim fails with DATASET_STORAGE_UNAVAILABLE;
control's file-owning path can claim that same attempt. The dataset and training
stores hold exclusive writer locks. Their maintenance verification operation is
also exclusive, so opening another full Store cannot provide online reader access.
Research and exact evidence: [published file readers](../research/training-published-file-readers.md).

## Proposed decision

Each owning package provides a concrete PublishedReader for an existing namespace.
The reader opens its own root and read-only carrier descriptors, exposes only
published-file verification/opening and Close, and never initializes storage or
takes/releases writer ownership. Existing writer and maintenance locks stay
exclusive. Each consuming service selects exactly one writer Store or concrete
PublishedReader at startup. A zero, closed or ambiguous component fails closed.

Keep current private path/UID/mode checks, bounded namespace/directory reads, exact
namespace/root/carrier identity, full publication receipt/inventory checks and
size/digest verification. Return the same read-only descriptor that was verified;
closing a reader cannot invalidate a returned file owned by its caller. Hash/copy
operations remain streaming and honor the caller's cancellation.

Dataset metadata reads retain their existing exact scope and retirement locks.
Training accepted sources retain their current job/attempt, physical stop,
configuration, result and inventory fences. Checkpoint transfer still decodes
and binds the accepted seal and repeats current authority after file verification.
Neither reader nor source snapshot authenticates a client, authorizes a lease or
caches authority across SQL transactions or file I/O.

The MVP file-access mechanism is explicitly local: the installation supplies the
exact retained namespace at its configured path, with read-only mount enforcement
and the existing private runtime owner. There is no inferred cross-host mount,
NFS/CSI support or new artifact RPC. The gateway composition owner must inject
the real consumers, close readers on startup failure and drain/join current users
before shutdown. No training, processing or GPU worker starts in the gateway.

## Consequences and acceptance boundary

The af5cefcd Go baseline passes its focused/race/storage tests, ordinary owner
packages and complete check/build on Darwin. The dc2db707 export follow-up
passes the ordinary owner packages and complete check/build on Darwin after
an earlier complete-gate attempt was refused before startup by the permanent
workstation guard. Native Linux descriptor and private
read-only bind prototypes independently prove writer exclusion, EROFS mutation
refusal and teardown using generated bytes. These are separate evidence scopes.
Tagged Go/SQL bodies, native Go owner acceptance and the installed gateway graph
remain unrun. The candidate is unmerged and no product item is ticked.

The reader does not repair SQL lock privileges. Dataset/version and local-cell
training-job locks still require protected fixed scoped row-returning functions
and formal migration/catalog/grant admission by their owners. Model lock rights
and the opaque Node fence remain separate. Direct arbitrary id UPDATE grants,
removed locks, success callbacks and privileged retry are rejected. Preserve the
original event/fleet budgets and the reproduced standalone gateway failure until
the complete real composition passes.
