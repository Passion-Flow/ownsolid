# Current native MVP and registry ownership

Current MVP backup/restore dispatch consumes the actual native owners and their
original journal/output custody. The registry uses an independent readonly signed
release volume with only its exact `/store` child covered by the separate writable
registry volume. Cold installation and fresh-M17-to-MVP forward preparation bind
both configuration payloads, the native recovery descriptor and original complete
release inventory. Unknown effects remain observation-only until reconciled.
The forward registry lifecycle has eight effects in the original27-phase edge;
the legacy M16-to-M17 edge retains its19 phases. An M17 produced by that legacy
edge cannot currently chain a second forward upgrade; legacy-restored M17 forward
is also an unimplemented retained combination. See the [current contract](../../../../../docs/execution/mvp/mvp-forward-code-20261103.md)
and [code-delivery profile](../../../../../docs/execution/mvp/code-delivery-profile-20261103.md).

The earlier checkpoint notes below retain their original execution limitations;
current code delivery does not relabel those historical runs or establish SQL,
large-artifact, installed-cluster or hardware qualification.

## Earlier native backup source checkpoint

`mvp_native_backup_controller.go` provides the separate cold-source execution
loop around one original writer and one original network-none verifier. It
retains the complete original tar and host tree, removes the exited writer before
the exclusive verifier, and reconciles unknown started effects without replay.
Abort retains the native artifact volume and host evidence. The shared dispatch
is not enabled in this checkpoint: physical storage mapping, original
restored-source admission, registry-role integration and actual composed native
execution are still required. Structural test doubles establish no SQL or
current-image acceptance.

`mvp_native_backup_storage.go` freezes six coexistence phases in the original
plan. SQL/store/native configuration limits stay with the original typed policy;
the projected configuration bytes and independent registry manifest limit come
from the actual admitted projection. Both the complete original tar and extracted
tree must fit the outer limit before any reservation. Native volume, host tar,
copied tree, wrapper, original journal/view files and scratch projections are
charged together when their
observed device is shared, with entry/block allowance, system30% floor and the
original minimum-free reserve. A missing actual native Engine host-root mapping
refuses before effects; virtual or inaccessible filesystem capacity cannot grant
admission. The narrow Engine observer verifies the kernel Unix peer, root dockerd
process and namespaces, original local-volume custody, actual canonical roots
and devices, rejecting nested/bind mounts. Scope binds that observation to its
original Engine/socket identity and independently rereads each allocation root.
The original Scope filesystem is charged independently when it differs. Fresh
capacity is not immutable source identity. The two SQL-sized
scratch allowances are conservative projections, not native filesystem quotas;
native process temporary growth and existing PostgreSQL data/WAL/server temporary
growth still require the coordinator's pinned-image, actual-backing case budget.
The source plan does not manufacture that evidence or qualify a VM backing file.

`mvp_native_backup.go` reserves exact original configuration/signed source bytes,
retains complete native observation stdout and publishes the distinct outer
inventory only after its caller has completed the original fixed verifier.
Explicit publication can resync an exact visible original file; partial or
changed files are retained and refused. Readonly inspection never publishes.

`mvp_native_source.go` owns the distinct format2 wrapper around the original
`native-postgresql/` candidate, complete record, original readback, SQL dump,
four store directories and supplementary registry payload. `plan.json`, source
signed manifest/signature, original configuration inventory and exact private
`native-observation.json` remain separate. It rehashes every payload/mode and
reconstructs original portable store/configuration/registry tree digests. The
public references retain the native request, candidate, signed source and outer
inventory digests independently. Original source versions come only from the
native owner's `mvp_source.source_metadata`; historical absent facts refuse.

`mvp_native_source_release_policy.go` retains the mandatory original
`release_view_binding`. The existing payload parser admits the MVP application
explicitly, while legacy `BackupPlan` selection stays unchanged. The original
three configuration envelopes and specifically referenced policy files must be
in the frozen inventory and match one policy bound to source scope, signed
manifest and configuration digests, with publisher UID distinct from the
verified native reader. Production additionally checks the actual Scope owner
UID. Missing bytes or binding refuse; readonly inspection never repairs them.
This original source policy grants no target exemption or publisher authority:
the target separately validates its already frozen policy against its own marker.

The private source accessor is not serializable. Pure source inspection records
structural/integrity observation of the retained originally verified source; it
starts no process, creates no native completion and acquires no target authority.
Producer publication must follow the actual original network-none complete
verifier and the original Scope journal. A target must separately journal import
of the exact complete tree and execute its own original network-none verifier
before the single full-native restore. The MVP dispatch stays closed until that
composed producer/target implementation and checks exist.

`mvp_native_source_projection.go` clones the existing JSON-compatible YAML input
profile. Its native-only flat configuration excludes operator/runtime DSN bytes,
preserves exact keyrings/locales, and maps only admitted original references.
Original prepared and active Control inputs remain immutable. The closed
[descriptor example](../../../../../config/examples/release/offline-native-postgres.example.json)
and [schema](../../../../../config/examples/release/offline-native-postgres.schema.json)
enter through existing protected `operator-config/native-postgres.json`, not
ambient environment or a second loader. Original typed native policy remains the
adjustable-value authority. `BackupTemplate` is a deployment input: Scope binds a
fresh original attempt nonce/path, actual stopped-source evidence, reason and
signed/current image context once before publication. Optional restore/initializer
inputs use the same descriptor and retain independent target authority. Runtime
env-file templates and ordinary YAML outside the owning JSON input profile are
currently refused explicitly. Configuring a path does not create or qualify its
volume, signed prepared registry release, store, current image or SQL owner.

Current structural tests use explicit synthetic objects; they establish no actual
native backup, SQL, installed runtime, browser or final signed delivery. Full
producer/transport/dispatch and current-image execution remain integration gates.

# Isolated installation scope

`mvp_native_restore_observation.go` binds the original Engine-decoded restore
output to an independently verified signed MVP source, its unchanged four domain
stores and supplementary registry. Original request, candidate and signed-source
hashes remain distinct. Repeated observations compare every original restore
fact while allowing only the fresh readonly observation digest to vary. Exact
stdout bytes and their digest remain private in the existing Engine envelope.
Missing original completion remains noncomplete; a completed original cannot
silently lose its completion or substitute another backup/import receipt.
`mvp_native_restore_custody.go` retains each exact original observation through
the existing exclusive private-file and parent-sync owner, returning the existing
`InputFile` descriptor. Reopen checks that descriptor and the complete original
output without writes. Fresh observations use separate operation-bound files;
their bytes/time never enter the invariant restore identity. The record helper
does not authorize task/output cleanup: the caller must first retain its descriptor
in the original owning journal. Real private-file controls use synthetic native
output and do not qualify an Engine effect or native SQL.
These binding controls do not run a native restore, persist its scope journal or
enable the still-pending full-native dispatch/reopen/TLS bridge. Signature, SQL,
store and original transaction authority remain with their existing owners.
`mvp_native_restore_context.go` admits the original completed runtime context only
when its native request, candidate, archive, source tenant/schema and exact target
match the original reservation and observation. It preserves the native candidate
binding rather than substituting the enclosing portable inventory digest.
`mvp_native_restore_actor.go` inspects only the recorded original physical task
and reads its original completion through the fixed Engine SDK. It requires the
same successful terminal task before and after that read; a recreated owned name,
unknown exit, missing completion or changed original context refuses admission.
Its narrow inspector interface contains no create, start, stop or remove method.
This helper does not start recovery, authorize cleanup or publish stage success.
`mvp_native_restore_completion_custody.go` retains the exact original completion
separately from observer stdout. It binds the SQL dump digest supplied by the
independent source reader, the original runtime context and the explicit released
lock state. Its readonly join requires the observer to name that exact completion
and its original intent, files, target and post-image. Private completion custody
must enter the owning journal before the original actor can be removed; these
helpers neither append that journal nor grant removal or qualification authority.
`InspectRestoreSource` selects the native source reader before the legacy split
archive reader whenever an original native marker is present. Partial, null or
invalid native evidence remains a native failure and cannot fall back to an old
source plan. This read dispatch does not enable native restore execution.
`mvp_native_restore_source_configuration.go` rereads the genuine native wrapper
and its original private role files, with the complete source result and each
file descriptor bound again. `restoreRetainedKeyInventory` shares the existing
byte/key checks with the unchanged legacy policy wrapper. Native target policy
rebinding remains a separate prerequisite; this reader supplies no policy
exemptions and constructs no legacy backup plan or task evidence.

Until the complete native dispatcher is integrated, `mvp_native_restore.go` fences
every selected MVP/schema29/native marker before the old SQL/database/store
effects and their completed fast returns. Schema29 cannot acquire a legacy
twenty-step SQL record or a generated legacy qualification context. This explicit

or alter the earlier omitted-field profiles.

The optional `native_postgresql` result field uses the canonical release-contract

The MVP producer must also populate the outer signed `Profile` and

## MVP native and forward integration

The native restore controller retains one original SQL writer, independent
read-only database/store stages, immutable request/context custody and guarded
abort cleanup. The native backup controller selects actual cold, restored or
completed-forward source facts. The forward controller binds the protected MVP
configuration inventory and a separate image-registry owner; original M17
markers, role maps and release-view facts remain preserved. Code/build evidence
and deployment, hardware and complete-artifact runtime qualification are tracked
separately under the urgent code-delivery profile.
